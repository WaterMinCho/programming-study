# 라이브 코딩 60분 운영표

라이브 코딩은 면접 전에 작은 코드베이스를 받아 읽고, 면접 시간에 면접관이 건네는 요구를 그 코드 위에서 고치는 전형입니다. 2026년 토스 커뮤니티 Frontend Developer 공고에는 사전 과제 대신 면접 1시간 30분 전에 코드베이스를 주고 라이브 코딩에서 함께 읽고 고친다고 적혀 있고, 이 프로그램은 코드를 받고 면접까지 1시간이 있다고 보고 미션을 짰습니다. 리크루터 안내에 적힌 시간이 다르면 그 시간에 맞춰 아래 비율을 줄이거나 늘리세요. 받은 코드를 읽는 시간과 면접 시간을 어디에 얼마나 쓸지 적은 표를 이 페이지에서는 운영표라고 부릅니다. 이 페이지는 읽기 60분, 면접 첫 5분의 코드 설명, 요구마다의 구현, 테스트와 정리, 15분 넘게 막혔을 때 순서로 운영표를 설명합니다. 끝까지 읽으면 미션 w01과 w03을 풀 때 읽기 시계와 단계 시계를 어떻게 쓸지 정할 수 있습니다.

## 읽기 60분은 실행부터 시작합니다

받은 코드를 열자마자 첫 파일부터 읽어 내려가면 60분이 파일 몇 개에서 끝납니다. 처음 5분은 코드를 돌리는 데 쓰세요. 의존성을 설치하고(`npm install`), 개발 서버를 띄워(`npm run dev`) 화면을 눌러 보고, 테스트를 돌려(`npm test`) 통과하는지 봅니다. 화면을 눌러 보면 어떤 앱인지 1분 안에 알 수 있고, 면접관의 요구는 그 화면의 동작으로 말해지므로 화면을 먼저 봐 두어야 요구를 바로 알아들을 수 있습니다. 미션에서는 의존성이 저장소 맨 위에 설치되어 있으니 `npm install`은 건너뜁니다.

실행이 끝나면 나머지 55분을 아래처럼 나눕니다.

- 5~20분, 진입점에서 데이터까지. 브라우저가 처음 읽는 `index.html`에서 시작해 가장 먼저 실행되는 코드 파일을 진입점이라고 합니다(Vite 앱이면 `src/main.tsx`). 진입점에서 최상위 컴포넌트, 화면 컴포넌트, 서버와 통신하는 파일 순서로 따라가며 데이터가 어디서 와서 어디에 저장되고 어디서 그려지는지를 세 줄로 적습니다.
- 20~40분, state와 effect. 어떤 값이 state이고 어떤 값이 그 state로 계산되는지, `useEffect`가 언제 다시 실행되는지, 불러오는 중·실패·빈 결과가 어디서 처리되는지 또는 처리되지 않는지 적습니다. 타입 파일에서 서버 응답의 모양을 봅니다.
- 40~50분, 테스트. 기존 테스트가 무엇을 보장하는지 읽고, 테스트가 화면 요소를 찾는 방법(`getByRole` 같은 것)과 서버 대신 가짜 응답을 끼우는 방법을 봅니다. 요구를 받으면 같은 방법으로 테스트를 더할 수 있습니다.
- 50~60분, 설명 메모. 다음 절의 순서로 3분 분량 설명을 적고, 고치고 싶은 곳과 그 이유를 하나 적습니다. 읽으면서 눈에 띈 빠진 처리(실패 화면 없음, 늦은 응답 처리 없음)는 면접관의 요구로 나오기 쉬우니 그 자리의 파일과 줄 번호를 적어 둡니다.

읽는 동안 코드를 고쳐 보는 것은 막지 않습니다. 다만 면접관은 받은 코드를 기준으로 요구를 말하므로, 실험한 변경은 면접 전에 되돌려 받은 상태로 두세요. 미션 w01과 w03의 코드는 파일 열 개 안팎이라 읽기 시간이 15분과 20분으로 짧고, 다섯 구간의 비율은 60분일 때와 같게 잡습니다.

## 면접 첫 5분은 코드 설명입니다

면접은 면접관이 "받은 코드를 어떻게 읽으셨는지 설명해 주세요"라고 묻는 데서 시작합니다. 미션에서는 이 설명이 0단계이고 3분 시계가 돕니다. 설명은 파일을 하나씩 읽어 내려가는 것이 아니라 아래 순서로 합니다. 예시 문장은 미션 w03(거래내역 불러오기)의 코드를 설명하는 경우입니다.

1. 무엇을 하는 앱인지 한 문장. "통장 탭을 누르면 그 통장의 거래내역을 가짜 서버에서 받아 목록으로 보여 주는 화면입니다."
2. 데이터의 길. 어디서 받아, 어디에 두고, 어디서 그리는지. "`api.ts`의 `getTransactions`가 응답을 돌려주고, 고른 통장 id는 `App`의 state에 있으며, `TransactionList`가 그 id로 요청을 보내 목록을 그립니다." 읽기 시간에 적어 둔 세 줄입니다.
3. 다시 실행되는 조건. "`TransactionList`의 `useEffect`는 의존성 배열에 `accountId`가 있어서 탭을 바꿀 때마다 요청을 다시 보냅니다."
4. 눈에 띈 점 하나와 그 이유. "응답을 기다리는 동안 빈 목록이 보이고 실패해도 표시가 없어서, 그 부분을 먼저 고치고 싶습니다."

3분이 지나면 미션은 말한 항목에 표시하라고 합니다. 항목은 위 순서와 같은 꼴이라, 설명 메모를 이 꼴로 적어 두면 표시할 때 빠뜨린 것이 보입니다.

```figure
파일: assets/l21-2.png
캡션: 그림 2. 3분 설명은 한 문장 요약, 데이터의 길, 다시 실행되는 조건, 눈에 띈 점 순서로 하고, 각각 30초에서 1분을 씁니다.
내용: 왼쪽에 0:00, 0:30, 1:30, 2:20, 3:00 눈금의 세로 시간축과 칸 넷. 칸마다 제목. 오른쪽에 칸과 같은 높이로 w03 의 예시 말 두 줄씩. 맨 아래에 회색 "파일을 하나씩 읽어 내려가지 않습니다" 메모에 가로줄.
```

설명이 끝나면 면접관이 첫 요구를 말합니다. 바로 타이핑하지 말고 요구를 내 말로 다시 말해 확인하세요. "생활비 통장을 누르고 바로 저축 통장을 누르면 저축 내역만 보여야 하고, 더 쓰지 않을 생활비 요청은 끊어야 한다는 말씀이지요?"처럼 말하면 면접관이 빠진 조건을 덧붙여 줍니다. 입력, 기대하는 화면, 손대도 되는 범위가 정해지지 않았으면 이때 묻습니다. 미션의 「스스로 점검」에도 "타이핑하기 전에 요구를 제 말로 다시 말하고, 정해지지 않은 부분을 물었습니다" 항목이 있습니다.

## 요구마다 작게 고치고 바로 확인합니다

실전에서 요구 하나에 쓰는 시간은 미션 기준으로 8분에서 15분입니다. 그 안에 아래 순서를 한 바퀴 돕니다.

1. 어디를 바꿀지 말합니다. "`TransactionList`의 effect가 함수를 돌려주게 하고, 그 함수에서 이전 요청을 끊겠습니다." 타이핑하기 전에 말하면 방향이 틀렸을 때 면접관이 바로 잡아 줍니다.
2. 요구를 만족하는 가장 작은 변경을 합니다. 이름 정리와 파일 나누기는 뒤로 미룹니다. 바꾸는 동안 무엇을 하는지 한 줄씩 말합니다. 말이 끊기면 면접관은 지원자가 막혔는지 생각 중인지 알 수 없습니다.
3. 요구에 나온 시나리오를 브라우저에서 그대로 눌러 보거나 테스트로 확인합니다. 미션에서는 [검사]가 이 확인을 맡고, 실제 면접에서는 `npm run dev` 화면과 `npm test`가 맡습니다.
4. 통과했으면 남은 시간에 다듬습니다. "동작은 됩니다. 이름을 정리해도 될까요?"처럼 묻고 하면, 면접관이 다음 요구로 넘어가고 싶을 때 끊을 수 있습니다.

실전 시간에는 코드를 대신 써 주는 자동완성을 끄세요. 면접관이 끄라고 요청하는 때가 있고, 켜 둔 채 연습하면 자동완성이 없는 자리에서 손이 멈춥니다. 미션은 [실전 시작] 때 껐는지 묻고 답을 기록에 남깁니다.

## 테스트와 정리는 마지막에 몰지 않습니다

기존 테스트는 요구 하나를 끝낼 때마다 돌립니다. 앞 요구에서 만든 동작이 뒤 요구를 고치다가 깨지는 일이 흔하고, 미션의 [검사]도 앞 단계 검사를 함께 돌려 깨진 단계를 빨간 줄로 보여 줍니다. 요구가 "제보가 들어왔어요"처럼 버그 수정이면 고치기 전에 그 제보를 브라우저에서 재현해 두세요. 고친 뒤 같은 동작을 다시 해 보면 고쳐졌는지 바로 압니다.

면접 끝 5분은 정리와 요약에 씁니다. 디버깅하려고 넣은 `console.log`를 지우고, 에디터가 표시하는 타입 에러를 확인하고, 바꾼 파일을 하나씩 짚으며 무엇을 왜 바꿨는지 말합니다. 못 한 것과 시간이 더 있으면 할 것도 먼저 말하세요. 지원자가 먼저 말하면 면접관은 그것을 찾아내려고 질문하지 않아도 되고, 지원자가 자기 코드의 한계를 안다는 것이 전달됩니다.

## 15분 넘게 막히면 방향을 확인합니다

같은 줄을 세 번째 고치고 있거나, 에러 메시지가 10분째 같거나, 검사 실패 문구를 읽지 않고 코드를 바꾸고 있다면 막힌 것입니다. 요구 하나의 목표 시간을 넘겼으면 혼자 더 붙잡지 말고 면접관에게 방향을 확인하세요. 지금까지 한 것, 막힌 곳, 생각하고 있는 후보 두 개를 말합니다. "effect에서 요청을 끊게 했는데 끊긴 요청이 실패 화면을 띄웁니다. 에러 이름으로 거르는 방법과 `signal.aborted`를 보고 건너뛰는 방법을 생각 중인데, 어느 쪽이 맞을까요?"처럼 후보까지 말하면 면접관은 하나를 고르거나 다른 길을 알려 줍니다. 같은 15분을 혼자 더 쓰는 것보다 지금 묻는 편이 다음 요구에 쓸 시간을 남깁니다.

미션에서는 [힌트 듣기]가 이 질문에 해당하고, 누른 시각이 기록에 남습니다. 힌트를 들은 것은 감점이 아니라 연습 항목이라서, 「스스로 점검」에 "힌트를 들은 뒤 방향을 바꿨습니다"가 있습니다. 목표 시간이 지나면 [다음 요구로 넘어가기]가 켜지는데, 실제 면접에서도 면접관이 다음 요구로 넘어가자고 하는 때가 있습니다. 넘어간 단계는 끝난 뒤 해설과 모범 답안 비교에서 확인합니다.

## 이 프로그램에서는 이렇게 연습합니다

미션은 터미널에서 아래 명령으로 진행합니다. 대괄호 안에는 화면에서 같은 일을 하는 단추를 적었습니다.

```
python study.py web get w03        [과제 받기] 코드를 내 폴더로 복사하고 읽기 시계를 시작합니다
python study.py web start w03      [실전 시작] 0단계 코드 설명 3분이 열립니다
python study.py web check w03      [검사] 0단계면 점검 항목, 그 뒤는 단계 검사를 돌립니다
python study.py web hint w03       [힌트 듣기] 누른 시각이 기록됩니다
python study.py web skip w03       [다음 요구로 넘어가기] 목표 시간이 지난 뒤 켜집니다
python study.py web finish w03     [끝내기] 해설, 모범 답안 비교, 스스로 점검이 열립니다
```

읽기 시계와 실전 시계는 기록된 시각으로 계산되어 프로그램을 껐다 켜도 이어지고, 일시정지는 없습니다. 실전 시간이 지나도 시계는 멈추지 않고 넘긴 시간을 따로 셉니다. 넘긴 시간이 10분을 넘거나 넘어간 단계가 있으면 7일 뒤 "다시 해 볼 미션"으로 오늘 복습에 한 번 나옵니다. `get --again`은 [다시 하기]로, 내 폴더를 처음 코드로 덮어쓰고 기록을 새 회차로 나눕니다.

## 면접에서는 이렇게 이어집니다

미션 w01(상품 목록에 검색 붙이기)은 읽기 15분, 실전 30분으로 이 운영표를 짧게 한 바퀴 도는 미션이고, w03(거래내역 불러오기)은 읽기 20분, 실전 45분에 요구 네 개가 이어집니다. 꼬리 질문 사슬 11-B 「합칠 때와 나눌 때」는 시간이 부족할 때 무엇부터 할지를 말로 묻습니다. 꼬리 질문에 답하는 순서는 학습 페이지 l20에 있습니다.
