# 이벤트 루프: 기다리는 동안 무엇이 실행되나요

`fetch`로 서버 응답을 기다리는 동안에도 화면의 버튼은 눌리고 입력창에는 글자가 들어갑니다. 브라우저가 어떤 코드를 언제 실행하고 화면을 언제 다시 그릴지 정하는 규칙을 이벤트 루프라고 합니다. 이 페이지의 앞 절들은 `console.log` 세 줄에서 시작해 `setTimeout`, Promise, 화면 그리기를 차례로 더해 가며 이 규칙을 설명하고, 뒤 절은 거래내역 검색 화면을 예로 들어 오래 걸리는 코드가 입력을 막을 때 고치는 방법과 방법마다 드는 비용을 다룹니다. 끝까지 읽으면 꼬리 질문 사슬 1-A와 1-B의 질문, 그리고 이 페이지의 출력 순서 문제에 답할 수 있습니다.

## 함수는 콜 스택에 쌓였다가 빠집니다

```js
function greet() {
  console.log('안녕하세요');
}
console.log('시작');
greet();
console.log('끝');
```

이 코드는 '시작', '안녕하세요', '끝' 순서로 찍힙니다. 자바스크립트 엔진은 지금 실행 중인 함수들을 콜 스택이라는 목록에 쌓아 두고, 맨 위에 있는 함수만 실행합니다. `greet()`를 부르면 `greet`가 콜 스택 맨 위에 올라가고, 그 안에서 부른 `console.log`가 끝난 뒤 `greet`도 끝나면 콜 스택에서 빠집니다. 그래서 마지막 줄의 '끝'은 `greet`가 빠진 다음에야 찍힙니다. 함수 밖에 있는 코드도 콜 스택 맨 아래에 한 칸(그림의 "스크립트" 칸)으로 올라가 있다가, 마지막 줄을 실행한 뒤에 빠집니다.

브라우저 탭 하나의 자바스크립트는 콜 스택 하나로 실행되어서, 실행 중인 함수가 끝나지 않으면 다른 코드는 기다려야 합니다. 이 콜 스택 하나로 코드를 실행하는 흐름을 메인 스레드라고 부르고, 화면을 그리는 일도 같은 메인 스레드에서 일어납니다.

## setTimeout 콜백은 콜 스택이 빈 뒤에 실행됩니다

```js
console.log('A');
setTimeout(() => console.log('B'), 0);
console.log('C');
```

기다리는 시간을 0으로 줬는데도 A, C, B 순서로 찍힙니다. `setTimeout`은 콜백을 바로 실행하지 않고 브라우저의 타이머에 맡긴 뒤 곧바로 끝납니다. 브라우저가 차례로 처리할 일 하나하나를 태스크라고 부르고, 태스크가 줄을 서서 기다리는 곳을 태스크 큐라고 합니다. 타이머 시간이 다 되면 브라우저는 콜백을 태스크로 만들어 태스크 큐에 넣습니다. 클릭 같은 사용자 입력을 처리하는 콜백도 태스크로 들어옵니다.

이벤트 루프는 콜 스택이 비면 태스크 큐 맨 앞의 태스크를 꺼내 실행합니다. 위 코드에서는 `console.log('C')`까지 실행되어 콜 스택이 빈 뒤에야 B를 찍는 콜백이 꺼내집니다. `fetch`도 요청을 브라우저에 맡기고 곧바로 끝나서, 응답을 기다리는 동안 콜 스택이 비어 있고 이벤트 루프는 그사이 들어온 클릭 태스크를 꺼내 실행합니다.

## Promise 콜백은 다음 태스크보다 먼저 실행됩니다

```js
console.log('A');
setTimeout(() => console.log('B'), 0);
Promise.resolve().then(() => console.log('C'));
console.log('D');
```

이번에는 A, D, C, B 순서로 찍힙니다. `then`에 넘긴 콜백은 태스크 큐가 아니라 마이크로태스크 큐라는 다른 줄에 섭니다. 이벤트 루프는 태스크 하나를 끝내고 콜 스택이 비면, 다음 태스크를 꺼내기 전에 마이크로태스크 큐가 빌 때까지 안의 콜백을 모두 실행합니다. 처음에 위에서부터 실행된 스크립트 전체도 태스크 하나라서, 그 스크립트가 끝나자마자 C가 찍히고 그 뒤에 태스크 큐의 B가 찍힙니다.

마이크로태스크 큐에는 `then`, `catch`, `finally`에 넘긴 콜백과 `queueMicrotask`로 넣은 함수, async 함수에서 `await` 다음에 이어지는 코드가 들어갑니다. 마이크로태스크를 실행하는 도중에 새로 들어온 마이크로태스크도 다음 태스크로 넘어가기 전에 같이 실행됩니다.


## 화면은 언제 다시 그려지나요

DOM을 바꾸는 코드를 실행해도 화면은 그 줄에서 바로 바뀌지 않습니다. 브라우저는 태스크 하나와 마이크로태스크를 다 처리한 뒤 화면을 다시 그릴 차례가 왔으면 그때 그립니다. 1초에 60번 화면을 바꾸는 모니터라면 그릴 차례가 약 16.7ms마다 옵니다. 그릴 차례가 오면 브라우저는 다음 그리기 직전에 실행해 달라고 `requestAnimationFrame`으로 등록해 둔 콜백을 먼저 실행하고, 스타일을 계산한 뒤 요소의 위치와 크기를 정하고 색과 글자를 칠합니다. 위치와 크기를 정하는 단계를 레이아웃이라고 하고, 색과 글자를 칠하는 단계를 페인트라고 합니다.

```figure
파일: assets/l01-4.png
캡션: 그림 4. 이벤트 루프는 태스크 하나, 마이크로태스크 전부, 그릴 차례가 왔으면 화면 그리기 순서로 한 바퀴를 돕니다.
내용: 맨 위에 "메인 스레드에서 도는 이벤트 루프 한 바퀴" 글자. 위 줄 칸 셋 "태스크 하나 실행" → "마이크로태스크 큐 비우기" → "그릴 차례인가?". 마지막 칸에서 "아니요" 화살표는 위로 돌아 첫 칸으로, "예" 화살표는 아래 줄 띠 "requestAnimationFrame 콜백 → 스타일 → 레이아웃 → 페인트"의 첫 칸으로 감. 띠 끝에서 그림 바깥을 도는 "다음 바퀴" 화살표가 첫 칸으로 돌아옴.
```

화면 그리기도 메인 스레드에서 일어나기 때문에, 태스크 하나가 오래 걸리면 그동안 화면이 멈추고 클릭도 처리되지 않습니다. 아래 코드를 붙인 버튼을 누르면 3초 동안 다른 버튼을 눌러도 반응이 없고, 입력창에 친 글자도 3초가 지난 뒤에야 나타납니다.

```js
button.addEventListener('click', () => {
  const end = Date.now() + 3000;
  while (Date.now() < end) {}
});
```

실행하는 데 50ms를 넘긴 태스크를 롱 태스크라고 부르고, Chrome 개발자 도구의 Performance 패널은 롱 태스크에 빨간 표시를 붙입니다. 입력이 끊겨 보이는 화면을 고칠 때는 이 패널에서 녹화를 해 어느 태스크가 길었는지부터 찾습니다.

마이크로태스크는 큐가 빌 때까지 실행되므로, 마이크로태스크가 끝없이 새 마이크로태스크를 만들면 그릴 차례가 오지 않습니다.

```js
function forever() {
  Promise.resolve().then(forever);
}
```

`forever()`를 부르면 그 탭은 멈추고 다시 그려지지 않습니다. `then` 대신 `setTimeout(forever, 0)`으로 이어 붙이면 태스크와 태스크 사이에 화면 그리기와 입력 처리가 끼어들어 탭이 멈추지 않습니다.

## 출력 순서를 한 줄씩 따라가 봅니다

콜 스택, 태스크 큐, 마이크로태스크 큐의 규칙을 함께 쓰는 문제입니다. 아래 설명을 읽기 전에 출력 순서를 먼저 적어 보세요.

```js
console.log('A');
setTimeout(() => console.log('B'), 0);
Promise.resolve().then(() => console.log('C'));
queueMicrotask(() => console.log('D'));
(async () => {
  console.log('E');
  await null;
  console.log('F');
})();
console.log('G');
```

1. 스크립트 태스크가 위에서부터 실행되어 A가 찍힙니다. `setTimeout`은 B 콜백을 타이머에 맡기고, 0ms가 지나면 B 콜백이 태스크 큐에 들어갑니다.
2. `Promise.resolve()`는 이미 값이 정해진 Promise라서 `then`에 넘긴 C 콜백이 바로 마이크로태스크 큐에 들어갑니다. `queueMicrotask`는 D 콜백을 그 뒤에 넣습니다.
3. async 함수는 부르는 순간 첫 `await`을 만날 때까지 동기로 실행되므로 E가 찍힙니다. `await null`을 만나면 함수는 멈추고, F를 찍는 나머지 부분이 마이크로태스크 큐의 D 뒤에 들어갑니다.
4. G가 찍히고 스크립트 태스크가 끝나 콜 스택이 빕니다.
5. 이벤트 루프가 마이크로태스크 큐를 앞에서부터 비워 C, D, F가 찍힙니다.
6. 다음 태스크로 B 콜백이 꺼내져 B가 찍히고, 출력은 A, E, G, C, D, F, B 순서로 끝납니다.

```figure

프레임:
1. 그림 3 과 같은 배치. 1번 줄 강조, 출력 'A'. (1400ms)

9. 마이크로태스크 큐 빈 표시 뒤 "B" 카드가 스택으로, 출력 'B'. 출력 칸 전체 "A E G C D F B" 강조. (2500ms)
```

두 번째 문제는 태스크 안에서 새로 생긴 마이크로태스크가 언제 실행되는지 묻습니다. 타이머 콜백 둘이 태스크 큐에서 기다리고, 그 가운데 첫 콜백이 실행되면서 `then` 콜백을 하나 더 만듭니다. 출력 순서를 먼저 적어 보세요.

```js
setTimeout(() => {
  console.log('타이머 1');
  Promise.resolve().then(() => console.log('타이머 1의 then'));
}, 0);
setTimeout(() => console.log('타이머 2'), 0);
Promise.resolve().then(() => console.log('스크립트의 then'));
console.log('스크립트 끝');
```

1. 스크립트 태스크가 타이머 콜백 둘을 차례로 타이머에 맡기고, '스크립트의 then'을 찍는 콜백을 마이크로태스크 큐에 넣은 뒤 '스크립트 끝'을 찍습니다.
2. 스크립트 태스크가 끝나 콜 스택이 비면 이벤트 루프가 마이크로태스크 큐를 비워 '스크립트의 then'이 찍힙니다.
3. 0ms가 지나 태스크 큐에 들어온 타이머 1 콜백이 먼저 꺼내져 '타이머 1'을 찍고, '타이머 1의 then'을 찍는 콜백을 마이크로태스크 큐에 넣습니다.
4. 타이머 1 콜백이 끝나면 이벤트 루프는 타이머 2 콜백을 꺼내기 전에 마이크로태스크 큐부터 비우므로 '타이머 1의 then'이 찍히고, 그 뒤에 '타이머 2'가 찍힙니다.

## 직접 해 보기

실행해 본 뒤에는 코드를 조금씩 바꿔 가며 순서를 다시 예상해 보세요. 바꾼 코드마다 출력 순서를 먼저 적고 실행해 본 뒤, 바로 다음에 이어지는 설명과 비교해 보세요.

- 첫 번째 문제에서 `setTimeout` 줄을 맨 아래로 옮겨도 B가 마지막에 찍히는지 확인해 보세요.
- 첫 번째 문제에서 `await null`을 `await new Promise((r) => setTimeout(r, 0))`으로 바꾸고, F가 어디에 찍힐지 적어 보세요.
- 두 번째 문제에서 `Promise.resolve().then(() => console.log('타이머 1의 then'))`을 `setTimeout(() => console.log('타이머 1의 then'), 0)`으로 바꾸고, '타이머 1의 then'이 어디에 찍힐지 적어 보세요.

### 바꾼 코드는 이렇게 찍힙니다

`setTimeout` 줄을 맨 아래로 옮겨도 B는 마지막에 찍힙니다. B 콜백은 스크립트 태스크가 끝나고 마이크로태스크 큐까지 빈 뒤에야 태스크 큐에서 꺼내지므로, `setTimeout`을 스크립트의 어느 줄에서 부르든 C, D, F보다 늦게 찍힙니다.

`await null`을 바꾼 코드는 A, E, G, C, D, B, F 순서로 찍힙니다. 바꾼 `await`이 기다리는 Promise는 B 콜백보다 나중에 맡긴 타이머가 끝나야 값이 정해지므로, F는 B 다음에 찍힙니다.

두 번째 문제를 바꾼 코드에서는 '타이머 1의 then'이 '타이머 2' 뒤에 찍힙니다. 새로 맡긴 타이머의 콜백은 태스크 큐에서 먼저 기다리던 타이머 2 콜백 뒤에 서기 때문입니다.

## 긴 작업이 입력을 막을 때는 어떻게 고치나요

앞 절들은 `console.log`만 찍는 짧은 코드로 이벤트 루프를 따라갔습니다. 이 절에서는 React로 만든 거래내역 검색 화면 하나를 놓고, 롱 태스크가 입력을 막는 모습과 고치는 방법을 차례로 봅니다. `TransactionSearch`는 부모 컴포넌트에게서 거래내역 2만 건을 `transactions` props로 받고, 사용자가 검색창에 글자를 치면 가맹점 이름에 그 글자가 든 거래만 `TransactionList`가 아래에 그립니다. 사슬 1-B에서 면접관이 보여 주는 코드와 같습니다.

```tsx
type Transaction = { id: string; store: string; amount: number };

function TransactionSearch({ transactions }: { transactions: Transaction[] }) {
  const [query, setQuery] = useState('');
  return (
    <>
      <input value={query} onChange={(e) => setQuery(e.target.value)} placeholder="가맹점 검색" />
      <TransactionList transactions={transactions} query={query} />
    </>
  );
}

function TransactionList({ transactions, query }: { transactions: Transaction[]; query: string }) {
  const visible = transactions.filter((t) => t.store.includes(query));
  return (
    <ul>
      {visible.map((t) => (
        <li key={t.id}>
          {t.store} {t.amount}원
        </li>
      ))}
    </ul>
  );
}
```

글자 하나를 칠 때마다 `setQuery`로 두 컴포넌트가 다시 렌더링되고, `TransactionList`는 2만 건을 다시 거른 뒤 남은 거래를 모두 다시 그립니다. React가 이 렌더링을 하는 동안 메인 스레드는 다른 일을 하지 못하므로, 그사이 친 글자의 입력 처리와 화면 그리기는 렌더링이 끝날 때까지 기다립니다. 한 번 거르고 그리는 데 300ms가 걸린다고 하면, 'r', 'e', 'a'를 100ms 간격으로 칠 때 뒤에 친 글자일수록 더 늦게 화면에 나타납니다.

### 어느 태스크가 긴지부터 잽니다

고치기 전에 롱 태스크가 실제로 생기는지, 생긴다면 어느 함수가 시간을 쓰는지부터 잽니다. Chrome 개발자 도구의 Performance 패널에서 녹화 단추를 누르고 검색창에 글자를 몇 개 친 뒤 녹화를 멈추면, Main 트랙에 그동안 실행된 태스크가 가로 막대로 그려집니다. 50ms를 넘긴 태스크에는 빨간 삼각형이 붙고 50ms를 넘은 부분이 빨갛게 칠해집니다. 그 태스크를 누른 뒤 아래쪽 Bottom-Up 탭을 열면 그 안에서 시간을 가장 많이 쓴 함수가 위에 나옵니다. 거르는 `filter`가 위에 오는지, React가 목록 항목(`li`)을 만드는 함수와 레이아웃이 위에 오는지를 보면 계산과 그리기 가운데 무거운 쪽을 알 수 있습니다.

개발자 컴퓨터는 사용자 휴대폰보다 빠른 경우가 많아서, Performance 패널의 CPU 설정을 4배 느리게 바꾸고 한 번 더 잽니다. 이 설정은 지금 컴퓨터를 기준으로 느리게 만들 뿐이라 휴대폰 CPU를 똑같이 흉내 내지는 못합니다. 잰 숫자를 적어 두었다가 고친 뒤에 같은 순서로 다시 재면, 고친 방법이 롱 태스크를 얼마나 줄였는지 비교할 수 있습니다.

### Promise로 감싸도 메인 스레드는 막힙니다

거르는 코드를 Promise로 감싸 비동기로 만들면 입력을 막지 않는다고 생각하기 쉽습니다. 아래 코드는 거르는 데 200ms가 걸린다고 보고 `while` 반복문으로 시간을 보냅니다. 코드만으로 클릭을 흉내 내려고, 클릭을 처리하는 콜백 대신 0ms 타이머를 먼저 걸어 둡니다. 무엇이 어떤 순서로 찍힐지 먼저 적어 보세요.

```js
setTimeout(() => console.log('클릭 처리'), 0);
new Promise((resolve) => {
  console.log('거르기 시작');
  const end = Date.now() + 200;
  while (Date.now() < end) {}
  resolve('거르기 끝');
}).then((message) => console.log(message));
console.log('스크립트 끝');
```

'거르기 시작', '스크립트 끝', '거르기 끝', '클릭 처리' 순서로 찍힙니다. `new Promise`에 넘긴 함수는 그 자리에서 바로 실행되므로 200ms 반복문은 스크립트 태스크 안에서 돌고, `then` 콜백은 마이크로태스크라서 스크립트가 끝나자마자 실행됩니다. 클릭을 대신한 타이머 콜백은 둘이 모두 끝난 뒤에야 꺼내집니다. Promise는 결과를 받는 때를 정할 뿐이라, 거르는 계산은 감싸기 전과 같은 메인 스레드에서 같은 시간을 씁니다.

### 입력이 멈춘 뒤에만 거릅니다

글자를 칠 때마다 거르지 않고, 입력이 멈추고 정한 시간이 지난 뒤에만 함수를 실행하게 하는 방법을 디바운스라고 합니다. 아래 `debounce`가 돌려주는 함수는 불릴 때마다 앞서 걸어 둔 타이머를 지우고 새 타이머를 겁니다. 코드 아래쪽은 'react'를 100ms 간격으로 한 글자씩 치고, 1000ms에 'reactive'를 친 경우를 타이머로 흉내 냅니다.

```js
function debounce(fn, wait) {
  let timer;
  return (value) => {
    clearTimeout(timer);
    timer = setTimeout(() => fn(value), wait);
  };
}

const filterList = debounce((q) => console.log('거르기:', q), 300);
['r', 're', 'rea', 'reac', 'react'].forEach((q, i) => {
  setTimeout(() => filterList(q), i * 100);
});
setTimeout(() => filterList('reactive'), 1000);
```

'거르기: react'와 '거르기: reactive'만 찍힙니다. 400ms에 'react'를 넘긴 뒤 300ms 동안 다시 불리지 않았으므로 700ms에 한 번 거르고, 1000ms에 넘긴 'reactive'는 1300ms에 거릅니다. 'r'부터 'reac'까지 넘긴 호출은 타이머가 끝나기 전에 다음 호출이 그 타이머를 지워서 한 번도 거르지 않습니다.

```figure
2. 100·200·300ms 에 're', 'rea', 'reac' 눈금. 앞 타이머 막대는 다음 눈금 자리에서 회색으로 잘리고 "지움" 표시. (1800ms)
```

React 화면에서는 검색어 값을 늦게 따라오게 만드는 훅으로 디바운스를 겁니다.

```tsx
function useDebouncedValue<T>(value: T, wait: number): T {
  const [debounced, setDebounced] = useState(value);
  useEffect(() => {
    const timer = setTimeout(() => setDebounced(value), wait);
    return () => clearTimeout(timer);
  }, [value, wait]);
  return debounced;
}
```

`value`가 바뀌면 React는 앞 effect가 돌려준 함수를 먼저 불러 앞 타이머를 지우고, 새 값으로 타이머를 다시 겁니다. 그래서 `wait` 동안 `value`가 바뀌지 않아야 `debounced`가 새 값으로 바뀝니다. `TransactionSearch`에서 `const debouncedQuery = useDebouncedValue(query, 300);`을 두고 `TransactionList`에 `query` 대신 `debouncedQuery`를 넘긴 뒤, `TransactionList`는 `memo`로 감싼 컴포넌트로 바꿉니다. `memo`로 감싼 컴포넌트는 props가 앞 렌더링과 같으면 다시 렌더링하지 않으므로, 글자를 치는 동안에는 입력칸이 든 `TransactionSearch`만 다시 렌더링되고 목록은 `debouncedQuery`가 바뀔 때 한 번 다시 그려집니다.

디바운스는 거르는 횟수를 줄일 뿐 한 번 거르는 시간은 줄이지 않습니다. 결과는 마지막 글자보다 300ms 늦게 바뀌고, 그때 실행되는 렌더링은 여전히 롱 태스크라서 그 순간 친 글자는 기다립니다. 300ms라는 값도 기기와 상관없이 정해 둔 값이라, 빠른 기기에서는 결과가 필요 없이 늦게 나옵니다. 그래서 디바운스는 글자마다 나가는 검색 요청처럼 횟수만 줄이면 문제가 풀리는 곳에 잘 맞습니다.

비슷한 방법으로, 정한 간격마다 많아야 한 번만 함수를 실행하게 하는 방법을 스로틀이라고 합니다. 스크롤하는 동안 지금 위치를 200ms마다 저장하는 것처럼, 이벤트가 계속 일어나는 동안에도 중간 결과가 필요할 때 씁니다.

### 일을 나눠 사이사이 메인 스레드를 내줍니다

거르는 계산이 무겁다면 2만 건을 한 번에 거르지 않고 몇 묶음으로 나눠 거를 수 있습니다. 한 묶음을 거른 뒤 다음 묶음을 `setTimeout(다음 묶음, 0)`으로 태스크 큐 뒤에 세우면, 묶음과 묶음 사이에 그동안 들어온 입력이 처리되고 그릴 차례가 오면 화면도 그려집니다. 아래 코드는 거래내역 데이터가 없어도 콘솔에 붙여 넣어 바로 돌려 볼 수 있게, 0부터 29999까지의 숫자 3만 건을 1만 건씩 나눠 7의 배수를 거릅니다. 클릭은 앞 절처럼 0ms 타이머를 먼저 걸어 흉내 냅니다.

```js
function filterInChunks(items, test, size, done) {
  const result = [];
  let i = 0;
  function work() {
    const end = Math.min(i + size, items.length);
    for (; i < end; i++) {
      if (test(items[i])) result.push(items[i]);
    }
    console.log(`${end}건까지 거름`);
    if (i < items.length) setTimeout(work, 0);
    else done(result);
  }
  work();
}

const items = Array.from({ length: 30000 }, (_, n) => n);
setTimeout(() => console.log('클릭 처리'), 0);
filterInChunks(items, (n) => n % 7 === 0, 10000, (result) => console.log(`결과 ${result.length}건`));
```

```figure
5. 그 뒤로 "1만 건" 막대 둘과 "결과 4286건" 칸이 이어짐. 두 줄의 "클릭 처리" 자리를 점선으로 이어 앞당겨진 만큼 표시. (2200ms)
```

묶음 사이를 `await null`이나 `await Promise.resolve()`로 띄우면 효과가 없습니다. `await` 다음 코드는 마이크로태스크로 이어지므로, 묶음 사이에 다른 태스크도 화면 그리기도 끼어들지 못합니다. `scheduler.yield()`를 지원하는 브라우저에서는 `await scheduler.yield()`로 메인 스레드를 내줄 수 있고, 이때 이어지는 코드는 `setTimeout`과 달리 줄 맨 뒤로 밀리지 않고 같은 우선순위의 다른 태스크보다 앞에 섭니다. MDN은 이 함수를 아직 일부 브라우저에서만 쓸 수 있다고 적고 있어서, 없을 때는 `setTimeout`으로 대신합니다.

나눠 거르면 전체 시간은 조금 더 걸리고, 거르는 도중에 새 검색어가 들어오면 앞 작업을 멈추는 코드도 따로 짜야 합니다. 목록 항목을 그리는 일은 이렇게 나누기 어려워서, 이 방법은 계산이 무거울 때 씁니다.

### React에서는 목록 렌더링을 뒤로 미룹니다

목록을 그리는 일이 무겁다면, 입력칸은 바로 바꾸고 목록은 조금 늦게 따라오게 해서 목록 렌더링의 우선순위를 낮출 수 있습니다. React의 `useDeferredValue(query)`는 `query`를 늦게 따라오는 값을 돌려줍니다. 글자를 치면 React는 먼저 이 값을 옛 검색어로 둔 채 다시 렌더링해 입력칸을 바꾸고, 이어서 새 검색어로 한 번 더 렌더링하는 일을 뒤에서 합니다.

```tsx
const TransactionList = memo(function TransactionList({
  transactions,
  query,
}: {
  transactions: Transaction[];
  query: string;
}) {
  const visible = transactions.filter((t) => t.store.includes(query));
  return (
    <ul>
      {visible.map((t) => (
        <li key={t.id}>
          {t.store} {t.amount}원
        </li>
      ))}
    </ul>
  );
});

function TransactionSearch({ transactions }: { transactions: Transaction[] }) {
  const [query, setQuery] = useState('');
  const deferredQuery = useDeferredValue(query);
  const isStale = query !== deferredQuery;
  return (
    <>
      <input value={query} onChange={(e) => setQuery(e.target.value)} placeholder="가맹점 검색" />
      <div style={{ opacity: isStale ? 0.5 : 1 }}>
        <TransactionList transactions={transactions} query={deferredQuery} />
      </div>
    </>
  );
}
```

`TransactionList`를 `memo`로 감싼 것은 먼저 하는 렌더링을 빨리 끝내기 위해서입니다. 먼저 하는 렌더링에서는 `deferredQuery`가 옛 검색어라 `TransactionList`의 props가 바뀌지 않고, `memo`로 감싼 컴포넌트는 props가 앞 렌더링과 같으면 다시 렌더링하지 않으므로 입력칸만 바뀌고 렌더링이 끝납니다. `memo`가 없으면 먼저 하는 렌더링에서도 목록을 다시 그려서 입력칸이 같이 기다립니다.

뒤에서 하는 렌더링은 도중에 새 글자가 들어오면 버려지고, React는 키 입력을 처리한 뒤 새 값으로 다시 시작합니다. 그래서 키 입력이 목록 렌더링을 기다리지 않습니다. 디바운스처럼 정해 둔 지연 시간이 없어서, 빠른 기기에서는 목록이 거의 바로 따라오고 느린 기기에서는 기기가 느린 만큼 늦게 따라옵니다.

목록이 잠깐 옛 검색어의 결과를 보여 주므로, 위 코드처럼 `query`와 `deferredQuery`가 다를 때 목록을 흐리게 해서 아직 바뀌는 중이라고 알립니다. 이 방법은 느린 일이 렌더링 안에서 일어날 때만 효과가 있습니다. React 문서도 렌더링 밖에서 하는 일, 예를 들어 글자마다 나가는 서버 요청을 줄이는 데는 디바운스와 스로틀이 여전히 쓸모 있고 `useDeferredValue`와 함께 써도 된다고 적고 있습니다.

뒤에서 하는 렌더링이 끊길 수 있는 때는 React가 새 목록을 계산하는 동안입니다. React는 새 화면을 끝까지 계산한 뒤에 DOM을 한꺼번에 고치고, 그다음 브라우저가 레이아웃을 계산합니다. 그래서 Performance 패널에서 DOM에 목록 항목을 넣는 일이나 레이아웃이 무거웠다면 `useDeferredValue`를 써도 그 시간은 줄지 않고, 그동안 친 글자는 기다립니다. 이때는 화면에 보이는 목록 항목만 골라 그리는 가상화로 한 번에 그리는 항목 수를 줄입니다.

### 계산을 웹 워커로 옮깁니다

거르는 계산 자체가 무거워서 나누거나 미뤄도 모자라면, 계산을 메인 스레드 밖으로 옮깁니다. 메인 스레드와 따로 도는 스레드에서 스크립트를 실행하게 해 주는 브라우저 기능을 웹 워커라고 합니다. 아래 `search-worker.js`는 처음에 받은 거래내역을 넣어 두었다가, 검색어가 오면 걸러서 남은 거래의 id만 돌려보냅니다.

```js
let transactions = [];

onmessage = (e) => {
  if (e.data.type === 'load') {
    transactions = e.data.transactions;
    return;
  }
  const ids = transactions.filter((t) => t.store.includes(e.data.query)).map((t) => t.id);
  postMessage({ seq: e.data.seq, ids });
};
```

화면 쪽 코드는 워커를 만들어 거래내역을 한 번 보내 두고, 검색어가 바뀔 때마다 번호를 붙여 보냅니다. `showRows`는 받은 id의 거래를 화면에 그리는 함수입니다.

```js
const worker = new Worker(new URL('./search-worker.js', import.meta.url), { type: 'module' });
worker.postMessage({ type: 'load', transactions });

let lastSeq = 0;
function search(query) {
  lastSeq += 1;
  worker.postMessage({ type: 'search', seq: lastSeq, query });
}

worker.onmessage = (e) => {
  if (e.data.seq !== lastSeq) return;
  showRows(e.data.ids);
};
```

2만 건을 거르는 동안에도 메인 스레드는 비어 있어서 입력을 받고 화면을 그립니다. 대신 드는 비용이 커서, 큰 CSV 파일을 읽어 나누거나 이미지를 처리하는 일처럼 화면과 상관없는 계산이 오래 걸릴 때 주로 씁니다.

- 워커는 DOM에 손댈 수 없습니다. 거른 결과를 받아 목록 항목을 그리는 일은 메인 스레드에 남으므로, Performance 패널에서 목록 항목을 그리는 쪽이 무거웠다면 워커로 옮겨도 나아지지 않습니다.
- `postMessage`로 주고받는 데이터는 공유되지 않고 복사됩니다. 2만 건을 글자마다 보내면 그때마다 복사하는 시간이 들어서, 위 코드는 거래내역을 처음에 한 번만 보내고 그 뒤로는 검색어와 id만 주고받습니다.
- 답은 메시지로 늦게 돌아오므로, 앞 검색어의 결과가 나중 검색어의 결과보다 늦게 도착할 수 있습니다. 위 코드는 메시지마다 번호 `seq`를 붙이고 마지막으로 보낸 번호의 결과만 그려서, 늦게 온 결과가 화면을 덮지 않게 합니다.
- 워커 파일을 따로 두고 번들러가 그 파일을 찾게 해야 합니다. Vite는 `new URL`을 `new Worker` 괄호 안에 바로 적은 코드를 보고 워커 파일을 찾아 함께 묶습니다.

### 잰 결과로 방법을 고릅니다

어느 방법을 쓸지는 처음에 Performance 패널에서 본 롱 태스크 안에서 무엇이 시간을 썼는지로 정하고, 고친 뒤에는 같은 순서로 다시 녹화해 롱 태스크가 줄었는지 확인합니다.

- 목록을 그리는 렌더링이 무겁다면 `useDeferredValue`와 `memo`로 목록 렌더링을 뒤로 미룹니다. 바뀌는 코드가 적고 입력은 바로 반영됩니다.
- DOM에 목록 항목을 넣는 일이나 레이아웃이 무겁다면 미뤄도 그 시간이 남으므로, 가상화로 한 번에 그리는 항목 수를 줄입니다.
- 글자마다 나가는 서버 요청이나 렌더링의 횟수를 줄이는 것으로 충분하다면 디바운스를 겁니다. 결과가 정한 시간만큼 늦게 나오는 것은 받아들여야 합니다.
- 거르는 계산 자체가 무겁다면 묶음으로 나눠 사이사이 메인 스레드를 내주고, 그래도 길면 웹 워커로 옮깁니다. 워커는 메인 스레드를 가장 많이 비워 주지만, 파일 구성과 메시지를 주고받는 코드가 가장 많이 바뀝니다.
