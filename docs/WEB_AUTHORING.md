# 웹 면접 준비 출제 안내

웹 면접 준비 트랙에 라이브 코딩 미션, 꼬리 질문 사슬, 학습 페이지를 넣는 사람이 보는 문서입니다. 파일 규격, 봉인·검증·말투 검사 명령, 출제자와 재풀이자와 검토자가 나눠 맡는 교차 검증 순서를 적었습니다. 알고리즘 여행의 규격은 [JOURNEY_AUTHORING.md](JOURNEY_AUTHORING.md) 에 있고, 봉인과 서명의 방식은 그 문서와 같습니다.

미션은 처음 보는 작은 React + TypeScript 코드베이스를 읽고 면접관의 요구에 맞게 고치는 연습이고, 사슬은 답에 나온 낱말을 붙잡아 원리까지 한 단계씩 더 묻는 질문 묶음이며, 학습 페이지는 두 가지에 필요한 개념을 채우는 읽을거리입니다. 실제 출제 문제를 옮겼다고 쓰지 않고, 앱 화면에 회사 이름·로고·실제 문구를 쓰지 않습니다. 회사 이름은 형식의 출처를 밝힐 때만 brief.md 에 적습니다.

## 1. 폴더와 파일

```
package.json, package-lock.json     검사 도구의 고정 스택(devDependencies 만). 저장소 맨 위
node_modules/                       검사 도구 설치 자리. 커밋하지 않습니다
.web-check/                         검사하는 동안만 생기는 폴더. 커밋하지 않습니다
web/
  index.json                        미션·주제·페이지의 순서와 제목
  terms.json                        맥락 검사에 쓰는 낱말 목록
  kit/                              검사 공통 도우미(setup.ts, render.tsx …)와 모든 미션 공통 점검 항목 self_check.md
  missions/w03/
    meta.json                       공개
    brief.md                        공개. 읽기 시간에 보이는 안내
    app/                            공개 템플릿. 학습자가 받는 코드
    assets/                         해설 그림
    sealed.json                     work/ 를 묶은 봉인 파일. 이것만 커밋합니다
    work/                           평문 작업본. 커밋하지 않습니다
      steps.md                      단계 요구, 검사 설명, 힌트, 통과 뒤 질문
      checks/step1.test.tsx …       단계 검사. 숨긴 검사는 checks/hidden.test.tsx
      solution/step1/ … stepN/      그 단계에서 바뀐 파일만
      explain.md                    해설
      followups.md                  꼬리 질문(사슬 문법, 사슬 id 는 w03-F)
      check.md                      이 미션에만 나오는 점검 항목
      review.json                   검토 서명(--sign 이 씀)
  drills/t03/
    meta.json                       공개. 주제와 사슬의 제목·목표
    sealed.json
    work/chains.md                  사슬 본문. 커밋하지 않습니다
    work/review.json
  learn/l03/
    meta.json                       공개
    page.md                         공개. 봉인하지 않습니다
    assets/3a-1.gif …               페이지 그림
    review.json
```

- 폴더에 `meta.json` 이 있으면 출제된 것으로 봅니다. 나머지는 목록에 "준비 중"으로만 보입니다.
- 미션의 `work/` 와 주제의 `work/` 는 `.gitignore` 가 막고, `sealed.json` 하나로 묶어 커밋합니다. 묶음은 base64 와 zlib 로 감쌌을 뿐이라 우연히 답을 보지 않게 가리는 용도입니다. 학습 페이지는 읽을거리라 봉인하지 않습니다.
- 그림 스크립트는 `tools/web_art/<페이지 또는 미션>.py` 에 두고 알고리즘 여행의 `tools/journey_art/draw.py` 로 그립니다(6절).

## 2. 목록과 낱말

### index.json

```json
{
  "format": 1,
  "missions": [{"id": "w01", "no": 1, "title": "상품 목록에 검색 붙이기", "level": "워밍업"}],
  "topics": [{"id": "t01", "no": 1, "title": "실행 모델과 이벤트 루프"}],
  "pages": [{"id": "l20", "title": "꼬리 질문에 답하는 법"}],
  "order": ["l20", "w01", "t07", "t06", "w03", "t03"]
}
```

`level` 에는 워밍업, 기본, 응용, 실전 가운데 하나를 적습니다. `order` 는 웹 홈의 이어서 할 일과 새 사슬 순서에 쓰이며 목록에 있는 id 만 적습니다. `web/` 아래에 폴더를 만들었으면 index.json 에도 넣어야 검증이 통과합니다.

### terms.json

```json
{
  "known": ["함수", "변수", "배열", "객체", "콜백", "Promise", "컴포넌트", "props", "state", "useEffect"],
  "terms": [
    {"term": "경쟁 상태", "page": "l03"},
    {"term": "마이크로태스크 큐", "also": ["마이크로태스크"], "page": "l01"}
  ]
}
```

`known` 에는 FE 지원자가 이미 안다고 보는 낱말을, `terms` 에는 어느 페이지에서 소개하는지 정한 낱말을 적습니다. `page` 의 페이지가 출제되어 있으면 그 페이지 meta.json 의 `defines` 에 같은 낱말이 있어야 합니다. 쓰는 규칙은 7절의 맥락 검사에 있습니다.

## 3. 미션

### meta.json

```json
{
  "format": 1,
  "id": "w03",
  "title": "거래내역 불러오기",
  "level": "기본",
  "prep_min": 20,
  "live_min": 45,
  "steps": [3, 10, 8, 15, 9],
  "hidden": false,
  "pages": ["l03", "l07"],
  "chains": ["3-A", "7-A", "w03-F"],
  "needs": ["l03"],
  "defines_inline": ["경쟁 상태", "정리 함수"],
  "sources": [{"what": "StrictMode 가 개발 모드에서 effect 를 한 번 더 실행함", "url": "https://react.dev/reference/react/StrictMode", "checked": "2026-10-21"}]
}
```

| 키 | 뜻 |
|---|---|
| `prep_min`, `live_min` | 읽기 시간과 실전 시간(분) |
| `steps` | 단계별 목표 분. 0단계(코드 설명)부터 셉니다. 합계가 실전 시간의 90% 를 넘으면 경고가 나오니 실측 뒤 고칩니다 |
| `hidden` | 요구에 나오지 않는 버그를 숨겼으면 true. `checks/hidden.test.tsx` 가 있어야 하고, 끝낼 때 한 번 돕니다 |
| `pages` | 해설 뒤에 안내할 학습 페이지 |
| `chains` | 이 미션과 묶인 사슬. 꼬리 질문 `w03-F` 를 넣어야 복습 목록에 들어갑니다 |
| `needs` | 이 미션의 글이 전제하는 학습 페이지. 그 페이지가 정의한 낱말을 설명 없이 쓸 수 있습니다 |
| `defines_inline` | 이 미션의 글 안에서 처음 소개하는 낱말 |
| `sources` | 숫자, 기본값, 버전에 따라 바뀌는 사실의 출처. `what`, `url`, `checked`(YYYY-MM-DD) |

단계 제목은 요구를 미리 드러내므로 봉인 안의 steps.md 에만 둡니다.

### brief.md

읽기 시간에 보이는 안내입니다. 어떤 앱인지, 실행하는 법, 파일 구성, 가짜 서버 동작, 읽으면서 답해 볼 질문만 씁니다. 요구를 미리 알려 주는 글은 쓰지 않습니다. 말투 검사가 brief.md 와 단계 제목·요구·검사·힌트가 15글자 넘게 겹치면 유출로 잡습니다.

### app/

학습자가 받는 템플릿입니다.

- `package.json` 에는 `name`, `"private": true`, `"type": "module"`, `scripts` 만 둡니다. `scripts` 는 `dev: vite`, `test: vitest run` 이고 `typecheck: tsc --noEmit` 은 두어도 됩니다. 의존성은 저장소 맨 위 `package.json` 의 것을 쓰므로 적지 않습니다.
- `vite.config.ts`(react 플러그인, `test.environment: 'jsdom'`), `tsconfig.json`, `index.html`, `src/` 를 둡니다.
- `src/api.ts` 는 가짜 서버입니다. 검사가 `vi.mock('@app/api')` 로 바꿔 끼울 수 있게 함수만 export 합니다. 개발 모드의 지연과 실패는 `import.meta.env.DEV` 일 때만 쓰고 주소 쿼리(`?fail=1`)로 켭니다. 개발 모드에서는 `main.tsx` 의 StrictMode 때문에 처음 요청이 두 번 나갑니다. 실패를 첫 요청 하나에만 주면 두 번째 요청이 성공해 실패 화면이 보이지 않습니다. 그래서 화면을 연 뒤 1초 안에 보낸 요청을 모두 실패시킵니다.
- 실제 저장소처럼 기존 테스트를 1~3개 두고 템플릿에서 통과하게 합니다.
- 바깥 주소(localhost 제외), 회사 이름, `node_modules`, `dist` 를 두지 않습니다. `app/` 전체 크기는 200KB 를 넘지 않게 합니다.

### work/steps.md

파서가 읽는 고정 제목으로 씁니다.

````markdown
## 0. 코드 설명

### 요구
> 면접관: 받은 코드를 어떻게 읽으셨는지 3분 정도 설명해 주세요.

### 점검
- 고른 통장 id가 `App`의 state에 있다고 말했습니다.

## 3. 앞 통장의 내역이 보인다는 제보

### 요구
> 면접관: "생활비 통장을 누르고 바로 저축 통장을 누르면 …" 고쳐 주세요.

(설명 문단, 선택. 요구에 나온 낱말을 소개할 때 씁니다)

### 검사
- 생활비 통장 요청을 붙잡아 둔 채 저축 통장을 누르고 … 저축 통장 내역이 보이는지 봅니다.

### 힌트
- "effect가 다시 실행되기 직전에 React가 부르는 함수가 있어요."

### 통과 뒤 질문
> 면접관: 검사는 통과했는데, 개발 모드로 띄우면 …
- [필수] …
````

- 단계 번호는 0 부터 이어지고 meta.json 의 `steps` 개수와 같아야 합니다.
- 0단계는 `### 요구` 와 `### 점검`(말한 것에 표시하는 항목)만 둡니다. 1단계부터는 `### 요구`, `### 검사`, `### 힌트` 가 있어야 하고 `### 통과 뒤 질문` 은 선택입니다. 통과 뒤 질문에는 [필수] 항목이 하나 이상 있어야 합니다.
- 화면은 `### 검사` 목록을 "검사는 아래 내용을 확인합니다." 아래에 보여 줍니다. 요구와 검사 설명은 학습자가 읽는 글이므로 ~니다 체로 씁니다.

### work/checks/

- 파일은 `step<k>.test.tsx` 이고 테스트 이름은 `"<k><a-z> <학습자용 문장>"` 입니다. 예) `test('3a 생활비 통장 응답이 늦게 와도 저축 통장 내역이 그대로 보입니다', …)`. 첫 낱말이 검사 id 가 되어 기록에 남고 나머지가 화면에 보입니다. 숨긴 검사의 id 는 숫자로 시작하지 않습니다.
- 학습자 코드는 `@app/…` 로만, 공통 도우미는 `@kit/…` 로만 import 합니다. 상대 경로 import 는 검증이 막습니다. `@kit/<이름>` 은 `web/kit/<이름>.ts` 나 `.tsx` 가 있어야 합니다.
- 검사는 구현 방식을 묻지 않고 화면(역할, 이름, 글자)과 가짜 서버 호출(횟수, 인자, signal)만 봅니다. 구현을 묻는 검사는 요구 글에 그 요구가 적혀 있을 때만 씁니다.
- 검사 하나하나는 브라우저에서 페이지를 새로 연 것처럼 시작합니다. `beforeEach` 에서 `vi.resetModules()` 를 부른 뒤 `@app/api` 와 `@app/App` 을 다시 불러와 씁니다. 그러지 않으면 모듈 범위에 둔 저장소나 캐시가 앞 검사의 값을 이어받아 브라우저에서는 맞는 풀이가 검사에서만 떨어집니다. 파일 맨 위의 `import '@app/App'` 은 남겨 둡니다. 학습자 코드에 문법 오류가 있으면 검사 파일을 불러올 때 드러나 화면이 문법 오류 안내를 보입니다.
- 시간이 걸리는 동작은 `vi.useFakeTimers()` 와 `userEvent.setup({ advanceTimers: vi.advanceTimersByTime })` 로 시계를 앞당깁니다.
- 검사 파일 하나는 5초, 열린 단계 전체는 15초 안에 끝나야 합니다.

### work/solution/

`solution/step<k>/` 에는 그 단계에서 바뀐 파일만 `app/` 기준 경로로 둡니다. 검증 도구가 `app/` 위에 step1 부터 차례로 덮어 단계별 모범 답안을 만들고, 화면의 비교도 같은 방식으로 만듭니다.

### work/explain.md, followups.md, check.md

- `explain.md` 의 H2 절은 「면접관은 무엇을 보았나요」, 「고치기 전 코드」(선택), 「모범 답안」, 「단계마다 무엇을 바꿨나요」입니다. 그림은 5절의 figure 블록으로 놓고 이름은 `w03-1` 꼴입니다.
- `followups.md` 는 4절의 사슬 문법으로 쓰고 사슬 id 는 `<미션>-F` 입니다.
- `check.md` 는 이 미션에만 나오는 점검 항목 목록입니다. 모든 미션 공통 항목은 `web/kit/self_check.md` 에 한 벌만 둡니다.

## 4. 드릴 사슬

### meta.json

```json
{
  "format": 1,
  "id": "t03",
  "no": 3,
  "title": "비동기 처리와 Promise",
  "page": "l03",
  "chains": [
    {"id": "3-A", "title": "늦게 온 응답이 화면을 덮을 때",
     "goal": "검색 요청의 응답 순서가 바뀌는 원인을 말하고, 정리 함수와 AbortController로 고치는 법을 설명합니다.",
     "secs": 60, "missions": ["w03"], "section": "3a", "defines_inline": ["경쟁 상태", "정리 함수"]}
  ],
  "sources": []
}
```

사슬 id 는 주제 번호로 시작합니다(`3-A`, `3-B`). `secs` 는 질문마다 주는 답 시간(초)이고 `section` 은 사슬을 끝낸 뒤 여는 학습 페이지 절의 키입니다. `goal` 은 화면에 그대로 보이는 학습자용 글이라 ~니다 체로 씁니다.

### work/chains.md

````markdown
## 3-A

(사슬 소개 문단)

(면접관이 보여 주는 코드 블록, 선택)

### Q1. 're'를 치고 곧바로 'react'를 쳤는데 화면에 're' 결과가 남았습니다. 왜 그럴까요?
- [필수] 요청은 보낸 순서대로 돌아온다는 보장이 없습니다. …
- [보충] 앞서 보낸 요청의 응답이 늦게 도착해 나중 요청의 결과를 덮는 문제를 경쟁 상태(race condition)라고 부릅니다.
> 막히면: 두 요청이 언제 나가고 언제 돌아오는지 시간 순서대로 말해 보세요.

### Q2. 어떻게 고치나요?
…

### 약한 답
> "응답이 늦어서 그런 것 같으니 로딩 표시를 넣겠습니다."

(왜 약한지 문단)

### 이어 말하기
> "요청은 보낸 순서대로 돌아온다는 보장이 없습니다. …"
````

- 사슬 id 와 개수는 meta.json 의 `chains` 와 같아야 합니다.
- 질문은 3~5개를 권장하고, 질문마다 [필수] 1~3개, [보충] 0~3개, 「막히면」 한 줄을 둡니다. 「막히면」은 그 질문에서만 쓸 수 있는 말로 씁니다.
- [필수] 항목은 낱말 하나가 아니라 원인이나 동작을 말하는 문장으로 씁니다. 학습자가 "그 문장을 말했나"로 표시하기 때문입니다.
- `### 약한 답` 은 인용 한 줄과 왜 약한지 문단을 꼭 둡니다. `### 이어 말하기` 는 선택입니다.

```json
  "needs": [],
  "sections": {"3a": "늦게 온 응답은 어떻게 화면을 덮나요", "3b": "여러 요청을 묶을 때 하나가 실패하면 어떻게 되나요"},
  "outputs": [{"block": 2, "expect": "react 결과\nre 결과"}],
  "sources": []
}
```

- `defines` 는 이 페이지가 소개하는 낱말이고, `needs` 는 먼저 읽어야 하는 페이지입니다. needs 가 서로 돌고 돌면 검증이 실패합니다.
- `sections` 의 값은 page.md 의 제목 글과 같아야 합니다. 사슬 meta.json 의 `section` 이 이 키를 가리킵니다.
- `outputs` 는 출력 순서를 묻는 코드 블록의 번호와 정답입니다. 번호는 figure 블록을 뺀 코드 블록을 1 부터 센 것이고, 그 블록은 node 로 돌릴 수 있는 `js` 블록이어야 합니다. `verify_web.py --pages` 가 node 로 돌려 대조합니다.

### page.md

H1 제목 하나와 H2 절로 씁니다. 절 제목은 독자가 묻는 문장이나 그 절에서 일어나는 일을 말하는 문장으로 씁니다. 낱말은 쓰기 전에 소개하고, 예시는 바로 앞 문장과 이어지게 쓰며, 다른 장면으로 건너뛰지 않습니다. 참고할 예시는 설계 자료의 `samples/learn_sample.md` 와 `web/learn/l03/page.md` 입니다.

그림은 `figure` 블록으로 놓습니다. 화면은 이 블록을 그림 파일과 캡션으로 바꾸고 프레임 설명은 보여 주지 않습니다.

````markdown
```figure
파일: assets/3a-1.gif
캡션: 그림 3A-1. 're' 요청이 'react' 요청보다 늦게 끝나 화면이 옛 결과로 돌아갑니다.
프레임:
1. 가로 시간축 아래에 're' 요청 막대가 0ms 에서 시작함. (1400ms)
2. 'react' 요청 막대가 200ms 에서 시작함. (1400ms)
```
````

- `파일:` 은 `assets/<이름>.gif` 나 `.png` 입니다. GIF 에는 `프레임:` 아래 번호 줄을 두 줄 이상 두고 줄 끝에 `(1400ms)` 처럼 시간을 적습니다. PNG 에는 `내용:` 한 줄을 둡니다.
- 캡션은 "그림 1." 처럼 번호로 시작하는 학습자용 글(~니다)이고 말투 검사를 받습니다. 프레임 설명과 내용 설명은 그림 제작용 메모라 ~함 체로 씁니다.
- 그림 파일이 아직 없으면 검증은 경고만 내고, 화면에는 캡션과 "그림 준비 중"이 보입니다.

출제 중에는 아래 순서로 돌립니다.

### 봉인

```bash
python3 tools/web_seal.py seal [w03 t03 ...] [--keep]    # work/ → sealed.json, 평문 삭제(--keep 이면 남김)
python3 tools/web_seal.py unseal [w03 t03 ...]           # sealed.json → work/
python3 tools/web_seal.py check                          # 봉인되지 않은 평문이나 풀리지 않는 sealed.json 이 있으면 실패
python3 tools/web_seal.py brief w03 --out ~/brief_w03    # 다시 풀 사람에게 줄 공개본
```

- seal 은 기존 sealed.json 의 내용과 평문을 합쳐 다시 묶고, 같은 파일이 둘 다 있으면 평문을 씁니다. 봉인한 파일을 지우려면 unseal 로 꺼낸 뒤 그 파일과 sealed.json 을 지우고 seal 합니다.
- brief 는 brief.md, meta.json 의 공개 키(title, level, prep_min, live_min, steps, hidden, pages, needs), 템플릿 `app/` 만 넣습니다. 단계 요구, 검사, 힌트, 해설, 모범 답안은 들어가지 않고, 저장소 안의 폴더에는 만들지 않습니다.

### 검증

```bash
python3 tools/verify_web.py                  # 출제된 미션·주제·페이지 전부
python3 tools/verify_web.py w03 t03 l03      # 적은 것만
python3 tools/verify_web.py --pages          # 학습 페이지만
python3 tools/verify_web.py w03 --runs 3     # 반복 안정성 검사 횟수(기본 5)
```

실패가 하나라도 있으면 1 로 끝납니다. 미션은 아래 단계를 차례로 봅니다.

| 단계 | 내용 |
|---|---|
| 1 형식 | index.json, terms.json, meta.json 의 키와 값, 템플릿 `app/`(package.json, 파일 구성, 크기, 바깥 주소, 회사 이름, 기존 테스트) |
| 2 비밀 파일 | steps.md 의 단계와 절, 검사 파일의 id·import·@kit 도우미, solution/step<k>/, explain.md 의 절, followups.md 의 사슬 꼴, check.md |
| 3 글 | 학습자에게 보이는 글(brief, 단계 글, 해설, 꼬리 질문, meta 의 title·goal, 검사 이름, 캡션, 표 칸)이 `tools/check_style.py` 를 통과하는지 |
| 4 템플릿 | 템플릿의 기존 테스트가 통과하고, 모든 단계 검사가 템플릿에서 실패하는지 |
| 5 단계 답안 | step1~k 를 덮은 코드에서 1~k단계 검사가 통과하고 k+1단계 검사는 실패하는지(단계가 미리 풀리지 않음) |
| 6 최종 답안 | 마지막 단계 코드에서 숨긴 검사가 통과하는지. typescript 가 설치되어 있으면 `tsc --noEmit` 도 봅니다 |
| 7 반복 | 마지막 단계 코드로 전체 검사를 5번 돌려 결과가 같은지(불안정한 검사를 막음) |
| 8 시간 | 열린 단계 전체 검사가 15초, 검사 파일 하나가 5초 안에 끝나는지 |
| 10 그림 | figure 블록의 파일 이름 규칙, 꼴, 한도와 가리키지 않는 그림 |
| 11 검토 서명 | `--sign`, `--require-review`(8절) |

주제는 1·2·3·11 단계를, 학습 페이지는 1·3·9(출력 순서 문제를 node 로 돌려 대조)·10·11 단계를 봅니다. 4~8 단계는 Node.js 22.12 이상과 저장소 맨 위 `node_modules`(`python study.py web install`)가 있어야 돕니다. 단계 검사는 학습자 화면과 같은 `webprep.checks` 로 돌리고, 템플릿과 단계별 답안은 `.web-check/_verify_<미션>/` 에 잠깐 만들었다가 지웁니다.

### 말투와 맥락

```bash
python3 tools/web_lint.py                       # 출제된 항목 전부
python3 tools/web_lint.py w03 t03 l03           # 적은 것만
python3 tools/web_lint.py w03 --checker PATH    # 바깥 말투 검사기 위치
```

말투는 저장소의 `tools/check_style.py` 로 보고, 환경 변수 `STUDY_TONE_CHECKER` 나 저장소 옆 `../_tools/check_doc_tone.py` 가 있으면 그 검사기로도 봅니다. 검사기가 건너뛰는 표 칸, figure 캡션, 그림 대체 글, meta 의 글, 검사 이름은 한 줄씩 뽑아 같은 검사기에 넘깁니다. 오류가 있으면 1 로 끝나고 경고는 사람이 보고 넘깁니다.

맥락 검사는 글마다 "알아도 되는 낱말"을 정하고 terms.json 의 낱말이 그 밖에서 나오면 오류로 잡습니다.

- 알아도 되는 낱말은 terms.json 의 `known`, 그 글의 `needs` 페이지(차례로 그 페이지의 needs 까지)가 정의한 낱말, 그 글의 `defines`·`defines_inline`, 같은 미션 안에서 앞 글(brief → steps → explain → followups 순서)이 정의한 낱말이 들어갑니다. 사슬은 그 사슬의 `defines_inline` 만 씁니다.
- 그 글이 정의하는 낱말은 처음 나오는 문장이 정의 꼴이어야 합니다. 정의 꼴은 낱말 뒤에 "(이)라고 합니다", "(이)라고 부릅니다", "(이)라는" 이 오거나 "는 … 부르는 말" 인 문장입니다. 처음에 그냥 쓰고 뒤에서 정의하면 오류, 끝까지 정의 꼴이 없으면 경고입니다.
- 코드 블록, 인라인 코드, 제목, 면접관 말(`> 면접관:`)은 보지 않습니다. 캡션은 그 그림이 놓인 자리까지의 본문을 기준으로 봅니다.

그 밖에 아래 규칙을 봅니다.

| 규칙 | 판정 | 예 |
|---|---|---|
| 영어 낱말·인라인 코드 뒤에 띄어 쓴 조사 | 오류 | "React 가 다시 그립니다" 는 "React가 다시 그립니다" 로 씁니다 |
| 가리키는 것이 없는 "위 코드", "아래 그림", "아래 명령", "위 표" | 오류 | 같은 절 안에 그 코드 블록이나 그림이 있어야 합니다 |
| 반말 질문 제목 | 오류 | "왜 그럴까?" 대신 "왜 그럴까요?" |
| brief.md 에 새어 나간 단계 요구 | 오류 | 단계 제목이 그대로 나오거나 요구·검사·힌트와 15글자 넘게 겹침 |
| 가짜 정의 | 경고 | "이것을 정리 함수라고 합니다" 처럼 무엇인지가 문장 안에 없음 |
| 절 끝의 외딴 짧은 문단 | 경고 | 한 문장짜리 짧은 문단으로 절을 닫음 |
| "예상해 보세요" 바로 뒤의 답 | 경고 | 예상해 보라고 한 같은 문단에서 바로 답을 말함. 실행해 보라고 한 뒤의 답은 봐주지 않습니다 |

사용자가 새 문장을 지적하면 그 문장을 `tools/check_style.py` 의 패턴에 넣습니다.

### 사람이 읽는 검사

검사기가 못 잡는 것은 사람이 읽습니다. 앞 글을 읽은 적 없는 사람이 그 글 하나만 읽고, 설명하지 못하는 낱말과 앞 문장과 이어지지 않는 문장에 표시합니다. 출제자가 아닌 사람이 읽고, 그럴 사람이 없으면 출제자가 이틀 뒤에 읽습니다.

- 예시 코드가 바로 앞 문장이 말한 것을 보여 주나요?
- 장면(앱, 화면, 데이터)이 절 중간에 바뀌면 바뀐다고 먼저 말했나요?
- 면접관 말이 앞 단계에서 학습자가 한 일에 이어지나요?
- 「막히면」 줄이 그 질문에서만 쓸 수 있는 말인가요?
- 숫자와 사실마다 `sources` 에 출처가 있나요?

## 8. 교차 검증

출제한 사람이 직접 확인하면 같은 착각이 요구, 검사, 해설에 함께 들어갑니다. 그래서 출제, 다시 풀기, 검토를 서로 다른 사람이 맡습니다. 저장소 주인은 학습자이기도 해서 자기가 풀 미션의 봉인 안 글을 PR 에서 먼저 보지 않고, 실측도 다른 사람이 맡습니다.

| 역할 | 하는 일 |
|---|---|
| 출제자 | brief.md, 템플릿, 단계 요구, 검사, 모범 답안, 해설, 꼬리 질문, 사슬, 학습 페이지, 그림을 씁니다 |
| 재풀이자 | 공개본(brief.md 와 템플릿)만 받아 실전 모드로 풉니다. 요구는 출제자가 단계마다 말로 건넵니다 |
| 검토자 | 모든 파일을 읽고 아래 확인 목록을 봅니다 |

### 순서

1. 출제자가 평문 작업본을 쓰고 `verify_web.py w03` 과 `web_lint.py w03` 을 통과시킵니다.
2. 출제자가 `web_seal.py brief w03 --out DIR` 로 공개본을 만들어 재풀이자에게 넘깁니다. 재풀이자는 봉인 안 글을 보지 않습니다.
3. 재풀이자가 실전 모드로 한 번 풉니다. 프로그램 안에서 풀면 `python study.py web get w03` 부터 `finish` 까지 명령으로 진행하고, `record.json` 의 단계 통과 시각이 남습니다. 출제자는 그 시각으로 meta.json 의 `steps` 목표 시간을 고칩니다.
4. 검토자가 아래 확인 목록을 봅니다. 고칠 곳은 검토자가 직접 고치지 않고 출제자에게 돌려보내며, 출제자가 고친 뒤 다시 봅니다.
5. 검토가 끝나면 검토자가 서명합니다.

   ```bash
   python3 tools/verify_web.py w03 --sign --writer "출제 1" --resolver "재풀이 2" --reviewer "검토 2" --finding "3단계 요구에 끊어 달라는 말을 더함"
   python3 tools/verify_web.py t03 --sign --writer "출제 1" --resolver "재풀이 2" --reviewer "검토 2"
   python3 tools/verify_web.py l03 --sign --writer "출제 1" --resolver "재풀이 2" --reviewer "검토 2"
   ```

   서명 전에 그 대상을 검증하고, 실패가 있으면 서명하지 않습니다. 미션과 주제의 review.json 은 `work/` 안에 쓰이고, 학습 페이지의 review.json 은 페이지 폴더에 쓰입니다. 이름은 스터디장이 정하는 꼬리표이고 저장소에 남습니다. 다시 서명하면 전에 남긴 findings 를 이어 씁니다.
6. 출제자가 `web_seal.py seal w03 t03` 과 `check` 를 돌린 뒤 커밋합니다. 봉인은 파일 내용을 바꾸지 않아 서명의 해시가 맞습니다.

review.json 은 아래 꼴입니다. `files` 는 review.json 을 뺀 그 항목의 공개 파일, 템플릿, 그림, 봉인 안 글의 sha256 입니다.

```json
{
 "format": 1,
 "writer": "출제 1", "resolver": "재풀이 2", "reviewer": "검토 2",
 "files": {"meta.json": "<sha256>", "brief.md": "<sha256>", "app/src/App.tsx": "<sha256>", "work/steps.md": "<sha256>"},
 "findings": ["3단계 요구에 끊어 달라는 말을 더함"]
}
```

`--require-review` 는 review.json 이 없거나, writer 가 resolver·reviewer 와 같거나, 서명 뒤에 바뀐 파일이 있으면 실패하고 바뀐 파일을 알려 줍니다. 서명 뒤에 한 글자라도 고쳤으면 다시 검토를 받고 서명합니다.

### 검토자 확인 목록

- brief.md 만 읽어도 앱을 띄우고 읽을 수 있고, 단계 요구가 새어 나가지 않았습니다.
- 요구 글에 적힌 것만 검사가 봅니다. 구현을 묻는 검사는 요구에 그 말이 있을 때만 있습니다.
- 힌트는 뒤로 갈수록 더 드러내고, 첫 힌트는 고치는 방법의 이름을 말하지 않습니다.
- 해설의 코드가 마지막 단계 모범 답안과 같고, 「단계마다 무엇을 바꿨나요」가 solution/ 의 차례와 맞습니다.
- 꼬리 질문과 사슬의 [필수] 항목을 낱말이 아니라 문장으로 썼고, 「막히면」을 그 질문에서만 쓸 수 있는 말로 썼습니다.
- 학습 페이지가 낱말을 쓰기 전에 소개하고, 예시가 바로 앞 문장이 말한 것을 보여 주며, 다른 장면으로 건너뛰지 않습니다.
- 숫자, 기본값, 버전에 따라 바뀌는 동작마다 `sources` 에 공식 문서 주소와 확인 날짜가 있습니다.
- 실제 출제 문제를 옮겼다는 말이 없고, 회사 이름은 형식의 출처를 밝힐 때만 나옵니다.
- `web_lint.py` 의 오류가 0 이고 경고를 하나씩 보고 넘겼습니다.

## 9. PR 점검표

PR 하나에 미션 하나 또는 주제 하나(그 학습 페이지 포함)를 넣고 본문에 아래를 적습니다.

- `web_lint.py` 출력(오류 0, 경고와 처리)
- 사람이 읽는 검사에서 나온 표시 수와 고친 곳
- `verify_web.py` 출력과 재풀이자의 실측 시간
- 출처 목록
- 실제 출제 문제를 옮겼다는 말이 없는지, 공고 인용이 형식 설명에 그쳤는지
