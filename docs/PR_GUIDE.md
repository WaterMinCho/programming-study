## PR 제목 형식과 예시

`종류(범위): 변경 내용` 형식으로 씁니다. 범위는 생략할 수 있고 콜론 뒤에는 한 칸을 띄웁니다. 제목은 전체 120자 이내로 쓰고 범위에는 영문·숫자와 `_`, `.`, `/`, `-`를 쓸 수 있습니다.

| 변경 | 제목 예시 |
|---|---|
| 첫 입력 실습 기록 | `docs(model): 공통 입력과 정답 모양 기록` |
| 모델 코드 추가 | `feat(model): LSTM 학습과 평가 추가` |
| 잘못된 동작 수정 | `fix(model): 빈 이력의 손실 계산 수정` |
| 검사 추가 | `test(model): 미래 풀이를 가리는 조건 확인` |

종류는 `feat`, `fix`, `docs`, `refactor`, `test`, `chore`, `style`, `perf`, `build`, `ci` 중에서 고릅니다. 제목 형식이 틀리면 [Edit]로 제목을 고칩니다. 새 커밋을 만들지 않아도 제목·본문 변경 시 검사가 다시 실행됩니다.

PR 본문에는 무엇을 바꿨는지, 어떤 입력으로 확인했는지와 실행하지 못한 조건을 적습니다. 기록은 `~함`, `~음`, `~했음`으로 씁니다. 긴 완료 목록 대신 한두 문단으로 설명합니다.

```text
feat(model): LSTM 학습과 평가 추가

공통 입력 버전 5의 합성 자료로 학습·평가·저장 코드를 추가했음. 빈 이력과 mask를 확인했으며 실제 수강생 자료의 학습은 실행하지 않았음.
```

담당 이슈와 연결하려면 PR 본문에 `관련 이슈 WaterMinCho/programming-study#119`처럼 적습니다. 이슈의 작업을 모두 마친 마지막 PR에는 `Closes WaterMinCho/programming-study#119`를 적으면 `main`에 머지될 때 이슈도 닫힙니다. 본인 번호로 바꾸는 방법과 연결 확인은 [담당 이슈와 PR 연결하기](LEARNING_WORKFLOW.md#이슈와-pr-연결)를 따르세요.

## 모델 코드와 실험 설명의 리뷰 기준

팀원은 `experiments/본인GitHubID/`에서 개발합니다. 모델 설명은 입력을 어떻게 읽었는지, 왜 그 방법을 골랐는지, 무엇을 실행했는지 본인 말로 적습니다. 프로그램 README용 문장 패턴이나 불릿 개수로 제출을 막지 않습니다. [코드 검토](LEARNING_REVIEW.md)에서 설명의 정확성과 이해하기 쉬운 문장을 함께 확인합니다.

모델 Python 파일을 바꾸면 **모델 제출 검사**가 바뀐 파일의 구문만 확인합니다. 작성자 ID와 관계없이 변경 목록에 있는 모델 폴더의 `.py` 파일을 확인합니다. 모델 실행이나 라이브러리 설치는 하지 않습니다. 입력·빈 이력·예측·학습·평가·저장 중 이번 변경에 해당하는 실행 결과는 작성자가 남기고 검토자가 확인합니다. 구문 통과를 모델 학습이나 성능 검증으로 쓰지 않습니다.

제목 형식과 검사 계획의 완료는 모든 개발 PR에서 확인합니다. 수정 요청이 있으면 같은 브랜치에서 고쳐 Push합니다. 검사와 현재 커밋의 검토가 끝난 뒤 운영자가 머지하며 팀원 PR은 자동 머지하지 않습니다.

## 변경 파일별 자동 검사

작성자·브랜치 이름·PR 제목으로 제품 검사를 생략하지 않습니다. 아래 경로는 저장소 맨 위에서 시작합니다.

| 실제로 바꾼 부분 | 자동 검사 | 코드 검토에서 확인할 내용 |
|---|---|---|
| `experiments/본인ID/`의 설명·설정 | 제목·검사 계획 확인 | 입력 이해, 설정의 이유, 관측 결과와 미실행 범위 |
| 같은 폴더의 Python 코드·테스트 | 위 검사와 바뀐 Python의 구문 검사 | 이번 코드의 배열·빈 이력·예측과 작성자의 실행 근거 |
| 등록한 공통 사용 안내 README | 문장·제목·검사 계획 확인. `learning_data/README.md`와 `learning_server/README.md`는 수집 서버 운영 검사도 실행합니다. | 현재 화면·사용법과 링크 |
| 새 `docs/*.md` 안내·규칙 문서 | 문장·기능 검사 | 연결·예제·검사 기준의 일치 |
| `learning_server/` 등 서버 코드 | 기능 검사·해당 Windows·Ubuntu 운영 검사 | 수집·입력·저장 동작과 경계 조건 |
| `gui/` 등 화면·공통 학습 코드 | 기능·문항·화면 검사 | 사용 흐름과 작은 창·글자 확대의 배치 |
| `problems/`, `ai/learning/`, `dungeons/`, `web/`의 학습 자료 | 기존 문항·봉인·기능·화면 검사 | 정답·해설·출처·그림의 일치 |
| 등록한 CI 도구·검사 연결 | 기능 검사·문장 검사 | 분기·누락·실패 전달과 알림의 일치 |
| 분류하지 못한 경로 또는 비교 실패 | 제품 전체 검사 | 새 경로의 영향과 분류 기준 |

모델 코드와 공통 화면을 함께 바꾸면 양쪽 검사를 모두 실행합니다. 파일을 다른 폴더로 옮겨도 삭제된 원래 경로를 검사 범위에 포함합니다. 비교에는 [GitHub PR에서 사용하는 분기점][pr-diff]을 사용합니다. 팀원 브랜치가 main보다 뒤에 있다는 이유로 main의 후속 수정까지 팀원의 변경으로 세지 않습니다.

공통 문서와 모델 설명을 함께 바꾸면 공통 파일과 PR 본문에만 프로그램 문서용 문장 검사를 적용합니다. 모델 설명은 코드 검토에서 읽습니다. 과거 풀이용 `submissions/`의 변경은 현재 모델 개발 절차에 사용하지 않습니다.

## 필수 검사 결과와 Skipped 표시

**변경 범위**에서 모델 파일·공통 파일 수와 계획한 검사를 확인합니다. **필수 검사**는 계획한 작업이 실제로 성공했는지 확인합니다. 실행하지 않기로 한 화면·기능 검사의 `Skipped`는 정상이며, 계획한 검사가 실패하거나 취소되면 필수 검사도 통과하지 않습니다.

모델 PR의 문장 검사에서 프로그램용 문장 검사를 적용하지 않았다고 나와도 검토를 생략한 것은 아닙니다. **스터디 코드 검토**에서 피드백을 확인합니다. 검토가 중단되거나 실행 근거가 없으면 완료로 표시하지 않습니다.

검사와 현재 커밋의 검토가 끝나면 [Slack 결과 카드](SLACK_NOTIFICATIONS.md)를 확인합니다. 모델 제출 검사도 끝난 뒤 종합 결과를 한 번 알립니다.
